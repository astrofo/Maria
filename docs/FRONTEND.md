# Подключение фронтенда к порталу «Дети Марии»

Бэкенд уже обслуживает веб-интерфейс из `public/` и JSON API под `/api`. Новый фронтенд можно разрабатывать отдельно и затем подключить к тому же API. Сервер сам проверяет роли, принадлежность записей пользователю и допустимость изменений.

Файл `integration/api-client.js` — готовый браузерный ES-модуль без сторонних зависимостей. Скопируйте его в `src/api-client.js` своего фронтенда. Он совместим с обычным JavaScript и сборщиками React/Vue/Vite. Это браузерный клиент: для SSR/Node потребуется отдельное управление cookie пользователя; автоматического общего серверного cookie-хранилища в модуле нет.

## Адаптация под новый макет

Текущий вид находится в `public/index.html`, `public/styles.css`, `public/portal-pages.css`, `public/app.js`; анкета — в `public/questionnaire.js` и `public/questionnaire.css`. Верстку и стили можно менять в этих файлах, сохраняя запросы и обработчики. Для отдельного React/Vue-фронтенда используйте `integration/api-client.js` и API-контракты ниже.

### Главная, регистрация и движение

На компьютерах и планшетах главное фото масштабируется по ширине баннера: боковые края и нижняя часть группы остаются в кадре, обрезается только верх здания. Пункт «Возможности» в публичном меню плавно прокручивает главную к «Найдите своё дело». Ссылки на карточках продолжают открывать список событий.

`public/motion.css` добавляет короткое появление экранов, карточек, диалогов и реакций кнопок. При системной настройке `prefers-reduced-motion: reduce` анимации и плавная прокрутка отключены.

Форма `#register` и ссылка «Зарегистрироваться» доступны независимо от флага открытия регистрации. Отправка формы разрешена только при `registration_enabled` и `email_verification_available`; при недоступности показано сообщение и отключена кнопка получения кода. Регистрация всегда требует настоящего письма. Наличие настроек почтового транспорта не доказывает доставку каждого письма.

Для ручной работы с демонстрационным волонтёром оператор может выполнить `node src/create-test-volunteer.js`, передав через stdin JSON с `email`, `password` и необязательным `full_name`. Адрес должен принадлежать домену `.test`; CLI создаёт только активного волонтёра, отказывается менять существующий аккаунт, не подделывает подтверждение почты и согласия и сохраняет действие в аудит. Вход в такой аккаунт выполняется по паролю; код `1234` доступен только если его точный адрес добавлен в `EMAIL_DEMO_ACCOUNTS`. Автоматического разрешения для всех адресов `.test` нет. Доступы хранятся отдельно от исходного кода и не входят в сборку.

### Телефоны, планшеты и компьютеры

Телефонная компоновка рассчитана на ширину 320–767 CSS px. Общая оболочка и главная находятся в `public/mobile.css`, который подключён последним; адаптация отдельных разделов — в их собственных CSS. Размеры определяются доступной шириной окна браузера.

На телефоне меню кабинета открывается кнопкой, закрывается выбором раздела, нажатием на фон или Escape. Фокус остаётся внутри открытого меню. Публичное меню содержит разделы главной, Кистика, анкету/регистрацию и чат; вход остаётся в шапке. Формы выстраиваются в одну колонку, размер текста в полях — не меньше 16 px, основные зоны нажатия — от 44 px. Учтены безопасные отступы экрана и динамическая высота браузера.

Карточки волонтёров используются на телефоне по умолчанию. Таблицы организатора и курсов преобразуются в вертикальные записи с подписями полей; остальные широкие таблицы прокручиваются в своём блоке. В мероприятиях, задачах и сообщениях на телефоне доступны отдельный список и выбранная запись с возвратом. Диалоги чата и Кистик учитывают изменение видимой области при открытии клавиатуры.

Сломанный режим предпросмотра ролей и кнопка «Посмотреть сайт» удалены. Старые ссылки `#role-preview/...` ведут в обычный кабинет текущего пользователя. Предварительная проверка анонса мероприятия, учебного материала и рассылки сохранена.

Широкие таблицы прокручиваются внутри собственного блока, который доступен с клавиатуры. Размеры полей навыков и расписания в анкете зависят от ширины карточки через CSS container queries. Для окон небольшой высоты уменьшены отступы, диалоги имеют собственную вертикальную прокрутку.

После получения макета сопоставьте его экраны с маршрутами API: вход → подтверждение почты (4 цифры) → анкета → кабинет выбранной роли. Для мероприятий, приглашений, задач и аналитики доступны описанные ниже серверные методы. Видимость элементов интерфейса должна соответствовать роли; сервер дополнительно проверяет доступ независимо от интерфейса.

При переносе форм сохраняйте cookie-сессию, CSRF, ведущие нули кода, состояния загрузки, ошибки полей и конфликт версии задачи. Новый дизайн не требует переноса или очистки базы. Для выкладки готовой сборки на том же сервере оставьте API по `/api`, а файлы фронтенда разместите в `public/`.

## Быстрое подключение

Создайте один экземпляр клиента на приложение:

```js
import { createApiClient, ApiError } from "./api-client.js";

export const api = createApiClient({ baseUrl: "/api" });

// При открытии приложения:
const config = await api.config();
let currentUser = null;
try {
  currentUser = (await api.profile.get()).user;
} catch (error) {
  if (error.status !== 401) throw error;
  // Покажите форму входа. Ошибка 401 здесь означает отсутствие сессии.
}

// При отправке формы входа:
const session = await api.auth.login(formEmail, formPassword);
currentUser = session.user;

// После входа:
const { items: opportunities } = await api.opportunities.list();
```

`baseUrl` включает префикс `/api`. Для одного адреса сайта оставьте `/api`. Для прямого обращения к другому разрешённому адресу используйте `https://АДРЕС_БЭКЕНДА/api`, учитывая ограничения cookie ниже. Адресом может быть домен или IP с доверенным HTTPS-сертификатом. Фактический адрес и доступность сервера сообщаются после развёртывания; этот документ не подтверждает публикацию конкретного сервера.

Не добавляйте `DATABASE_URL`, `SESSION_SECRET`, пароль администратора или другие серверные секреты в переменные `VITE_*`, клиентский код или сборку.

## Локальная разработка через Vite

Для повседневной разработки запускайте локальную демонстрационную копию бэкенда командой `npm run demo` из корня этого проекта. Её адрес — `http://localhost:3000`; данные и доступы сохраняются в `.local/`. Входите через подготовленные демонстрационные аккаунты: для регистрации используйте настроенную почту и `EMAIL_CODE_MODE=random`. Код `1234` доступен только для входа существующих аккаунтов из точного списка `EMAIL_DEMO_ACCOUNTS`, описанного ниже. Затем запускайте отдельный фронтенд на порту 5173 с прокси для API:

```js
// vite.config.js в проекте фронтенда
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    port: 5173,
    strictPort: true,
    proxy: {
      "/api": {
        target: "http://localhost:3000",
        changeOrigin: false,
      },
    },
  },
});
```

Клиент по-прежнему использует `baseUrl: '/api'`. С точки зрения браузера фронтенд и API находятся на `http://localhost:5173`. Если локальный бэкенд запускается с фиксированным `PUBLIC_ORIGIN`, который отличается от адреса Vite, добавьте `http://localhost:5173` в `FRONTEND_ORIGINS` бэкенда и перезапустите его. При `changeOrigin: true` такой allowlist также нужен, поскольку прокси может изменить `Host`, сохранив исходный `Origin` браузера.

Если нужен доступ именно к удалённому рабочему API через dev-прокси, запускайте Vite по HTTPS с сертификатом, которому доверяет браузер, настройте HTTPS `target` и добавьте точный HTTPS origin Vite в `FRONTEND_ORIGINS`. Рабочие cookie имеют флаг `Secure`: не рассчитывайте на передачу этих cookie через обычный HTTP dev-сайт. Сохраните проверку TLS-сертификата прокси и флаги cookie. Проще всего проверять интеграцию на локальной демонстрационной базе, а общую версию размещать под одним HTTPS-адресом.

## Размещение нового фронтенда

Рекомендуемая схема: один HTTPS-адрес, `/api/*` проксируется к Node.js, остальные пути обслуживают сборку фронтенда. У браузера остаётся один origin; `baseUrl: '/api'` работает без изменений. Текущий монолит уже устроен так для файлов в `public/`. Если заменить их сборкой SPA, настройте возврат её `index.html` для клиентских маршрутов, не перехватывая `/api/*`.

При разных origin бэкенд поддерживает точный список разрешённых фронтендов:

```dotenv
# В серверном окружении; примеры адресов нужно заменить своими.
PUBLIC_ORIGIN=https://api.example.org
FRONTEND_ORIGINS=https://volunteers.example.org,https://localhost:5173
SESSION_COOKIE_SECURE=true
```

`FRONTEND_ORIGINS` — список через запятую. Разрешены только точные `http://` или `https://` origin с портом при необходимости, без путей, query, `*`, логинов и паролей. Origin рабочего бэкенда из `PUBLIC_ORIGIN` разрешён и без включения в список. После изменения окружения перезапустите приложение.

CORS разрешает credentials, методы `GET`, `HEAD`, `POST`, `PATCH`, `OPTIONS` и заголовки `Content-Type`, `X-CSRF-Token`. Фронтенду доступны ответные заголовки `Content-Disposition` и `Retry-After`. Cookie `dm.sid` остаётся `HttpOnly`, `SameSite=Lax`, host-only. Поэтому разрешение CORS само по себе не даёт работу сессии между несвязанными сайтами: например, фронтенд на одном домене и API по чужому IP могут быть cross-site, и браузер не отправит cookie. Для такой схемы используйте `/api`-прокси на адресе фронтенда. Поддомены одного сайта также требуют точного CORS allowlist и HTTPS, если запрос идёт прямо между ними.

## Сессия и CSRF

Бэкенд использует cookie-сессию; Bearer/JWT-токены не нужны. Cookie `dm.sid` устанавливается сервером и недоступна JavaScript. Клиент всегда передаёт `credentials: 'include'`.

1. Перед первым изменяющим запросом клиент получает `GET /api/auth/csrf` → `{ "csrfToken": "…" }`.
2. Для каждого `POST` и `PATCH`, включая вход и регистрацию, клиент отправляет этот токен в `X-CSRF-Token`.
3. Вход, успешное подтверждение почты и смена пароля создают новую сессию и возвращают новый `csrfToken`. Клиент автоматически заменяет старый токен. Начало регистрации возвращает `202` и сохраняет текущую анонимную сессию и её CSRF-токен.
4. Выход возвращает `204 No Content`. Клиент удаляет токен из памяти.
5. При `401` на закрытом маршруте покажите вход заново. При `401` на форме входа покажите сообщение о неверных данных, сохранив форму.

Клиент хранит CSRF только в памяти, не в `localStorage`. При явном `403` с `code: 'CSRF_INVALID'` он один раз получает свежий CSRF и повторяет запрос: эта ошибка возникает до выполнения операции. Сетевые ошибки, `409`, `429` и общие серверные ошибки автоматически не повторяются, чтобы не создать дублирование действий. После сетевой ошибки во время записи сначала обновите соответствующий список и уточните, сохранилась ли запись.

```js
await api.auth.login(email, password);
await api.auth.changePassword(currentPassword, newPassword);
await api.auth.logout();
```

Смена пароля завершает остальные сессии пользователя. Актуальная роль проверяется в базе на каждом запросе; роль из состояния фронтенда используется только для отображения навигации.

## Почта и точные исключения для тестовых аккаунтов

В production используется `EMAIL_CODE_MODE=random`, `MAIL_TRANSPORT=unisender_go` и явно заданный список `EMAIL_DEMO_ACCOUNTS`. Обычные коды состоят из четырёх случайных цифр, значение `1234` исключено. Регистрация всегда почтовая; адреса тестового списка зарезервированы для уже существующих аккаунтов и не могут регистрироваться повторно. SMTP остаётся альтернативным транспортом. Данные провайдера, ключ и список тестовых адресов не нужны фронтенду; конфигурация сервера описана в [MAIL.md](MAIL.md).

`GET /api/config` возвращает `email_code_mode: "random"`, `email_login_available`, `email_verification_available`, `password_recovery_available` и `email_demo_login_available`. Первые три флага доступности относятся к настроенному реальному транспорту. Последний означает, что включён точный список тестового входа; он не разрешает код `1234` для произвольного адреса. Общего `email_demo_code` в конфигурации нет. Форма входа по коду доступна, когда `email_login_available || email_demo_login_available`; форма регистрации по-прежнему зависит от `registration_enabled && email_verification_available`.

Только ответ `POST /auth/login-code/request` для адреса из точного тестового списка содержит `delivery: "demo"` и `demo_code: "1234"`. Обычные ответы содержат `delivery: "email"` без самого кода. Клиент сохраняет способ доставки вместе с email и сроками конкретного незавершённого запроса, а не выводит его из глобального режима. Подсказка `1234`, подпись OTP и текст повторного запроса применяются только к этому тестовому запросу. При смене email нужно начать новый запрос. Даже для адреса из тестового списка вход возможен только в существующий незакрытый аккаунт.

`user.email_demo_account` отмечает авторизованный тестовый аккаунт. Только его кабинет показывает тестовую отметку и сообщает, что код не подтверждает владение почтой; профиль не показывает ложную отметку подтверждения. Общего демонстрационного баннера для обычных посетителей нет. Вход с паролем сохранён для всех. Восстановление пароля письмом для тестового адреса возвращает `403` с `code: "demo_password_recovery_disabled"`; для обычных пользователей оно доступно при настроенной почте.

Запросы кодов сохраняют сессию, CSRF, время действия и ограничения попыток. Тестовый вход не устанавливает `email_verified_at`. Согласия обязательны; исключение проверки подтверждённой почты при отправке анкеты действует только для точного тестового списка. Роли дополнительно проверяются сервером.

## Вход кодом из письма

`api.auth.requestLoginCode(email)` для существующего незакрытого аккаунта ставит письмо в очередь монолита. Для точного тестового списка действует описанное выше исключение без отправки письма. Код используется через `api.auth.verifyLoginCode(email, code)` в той же браузерной сессии. Повторная отправка использует `requestLoginCode` ещё раз. Регистрационные `verifyEmail` / `resendCode` для входа не подходят.

Если почты нет в `users`, запрос кода и вход по паролю возвращают `404` с `code: "account_not_found"` и сообщением «Аккаунт с этой почтой не найден. Зарегистрируйтесь или завершите подтверждение почты.». Клиент остаётся на форме входа, показывает ошибку и ссылку на регистрацию; экран ввода кода не открывается и письмо не отправляется. Незавершённая регистрация ещё не является аккаунтом: пользователь должен подтвердить почту. Закрытый аккаунт получает `403` с `code: "account_unavailable"`. Неверный пароль существующего незакрытого аккаунта сохраняет ответ `401`. Ограничения запросов по IP действуют и для этих ошибок.

Код одноразовый, действует 10 минут. Ограничения: одно письмо в 30 секунд, до пяти отправок в час на почту, до пяти неверных попыток в час и десяти за сутки; дополнительные ограничения действуют по IP. Повторная отправка не обнуляет счётчик неверных попыток. Закрытый аккаунт и изменение версии авторизации делают ранее выданный код недействительным. После успешного входа SID и CSRF обновляются.

`email_login_available` означает наличие конфигурации отправки, а не проверенную доставку писем. Закрытие самостоятельной регистрации не закрывает вход существующим пользователям по коду. Если почтовый транспорт недоступен или письмо не приходит, интерфейс предлагает вход с паролем; тестовый вход остаётся доступным отдельно через `email_demo_login_available`. Код для отправки зашифрован в очереди AES-GCM, проверочный код хранится как HMAC; данные `pending_login_codes` исключены из пользовательских выгрузок и новых резервных копий. Доставка выполняется в том же процессе Node.js, отдельный сервис не требуется.

## Общие форматы

- Все пути в таблицах ниже указаны без общего префикса `/api`.
- Тело запросов — JSON; максимальный размер 64 КБ. Поля используют `snake_case`.
- Коллекции возвращают `{ items, page, page_size, total, pages }`, отдельные записи — `{ item: {...} }`. Пользователи возвращаются в `user`, отклики — в `application`.
- `id`, `user_id`, `opportunity_id` и другие PostgreSQL `BIGINT` могут приходить строками. Сравнивайте через `String(id)`; готовый клиент принимает строковый или числовой положительный ID.
- `hours` и `total_hours` могут приходить десятичными строками: используйте `Number(value)` для вычислений.
- Момент времени передаётся ISO 8601 в UTC, например `2026-11-14T08:00:00.000Z`. Для `datetime-local` используйте `new Date(input.value).toISOString()`.
- `birth_date` и `participated_on` — календарные даты `YYYY-MM-DD`. Не преобразуйте их через локальный часовой пояс.
- `skills` и `interests` — массивы строк, до 30 элементов по 80 символов. `match_score` — число совпадающих тегов; это простая подсказка, а не автоматическое решение о допуске.

## Постраничные списки

Списки возвращают **`{ items, page, page_size, total, pages }`**. Передавайте `page` от 1 и `page_size` от 1 до 100; по умолчанию — 50. `total` и `pages` относятся ко всей выборке с текущими фильтрами. `pages` не меньше 1; запрос за последней страницей вернёт пустой `items`. Не считайте `items.length` общим количеством записей и не загружайте последовательно все страницы для обычного отображения списка.

Сохраняйте фильтры при переключении страниц, а при изменении фильтра сбрасывайте `page` в 1. Если после изменения данных текущая страница исчезла, переходите на последнюю существующую. Участие и обучение дополнительно возвращают `summary` для всей отфильтрованной выборки; суммы по текущему `items` охватывают только одну страницу.

| Список                            | Фильтры кроме `page` / `page_size`                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------- |
| `/opportunities`                  | `q`, `status`, `city`, `format`, `skill`, `interest`, `date_from`, `date_to`, `available`, `sort` |
| `/opportunities/:id/participants` | `q`, `status` отклика                                                                             |
| `/opportunities/:id/invitations`  | `q`, `status: active \| revoked`                                                                  |
| `/applications`                   | `opportunity_id`, `user_id`, `status`, `date_from`, `date_to` по дате отклика                     |
| `/participation`                  | `user_id`, `opportunity_id`, `date_from`, `date_to` по дате участия                               |
| `/users`                          | `q`, `city`, `skill`, `status`, `role`                                                            |
| `/training`                       | `q`                                                                                               |
| `/thanks`, `/audit`               | —                                                                                                 |
| `/notifications`                  | `unread: true \| false`                                                                           |

Даты фильтров — `YYYY-MM-DD`, границы включены. Отсутствующий фильтр не отправляйте. Права доступа применяются до пагинации и вычисления `total`.

### Фильтры возможностей и курсов

`GET /api/public/opportunities` и `GET /api/opportunities` поддерживают одинаковые фильтры, с учётом прав доступа. Публичный список допускает статусы `open` и `closed`; список сотрудника — также `draft`. Параметры `city`, `format`, `skill` и `interest` задают точное совпадение без учёта регистра и пробелов по краям, а `q` — текстовый поиск. Даты ограничивают дату начала в UTC; если начальная дата позже конечной, сервер возвращает ошибку валидации.

Для вариантов полей используйте `GET /api/public/opportunities/options/filters` или `GET /api/opportunities/options/filters`. Ответ: `{ cities, formats, skills, interests }`. Значения собираются из всех доступных пользователю мероприятий, не только текущей страницы; пустые значения и дубли убраны, каждый список ограничен 100 вариантами. Клиентские методы: `api.publicOpportunities.filterOptions()` и `api.opportunities.filterOptions()`.

`available=true` оставляет мероприятия с открытым набором, свободными местами и неистёкшими сроками проведения и приёма заявок. Это не проверка личного допуска: прохождение обучения и решение координатора учитываются отдельно. Отсутствие параметра или `false` не ограничивает выборку.

Сортировка `sort=soonest|latest|newest`: по дате начала вперёд, по дате начала назад или сначала недавно добавленные; по умолчанию `soonest`. При сортировке по дате записи без даты идут после датированных. Фильтрация и сортировка выполняются до пагинации. Интерфейс сохраняет условия при возврате из карточки и сбрасывает номер страницы при их изменении.

Каталог `/api/courses` поддерживает `q`, `topic`, `type`, `status` и `sort=newest|title|duration`. Сортировка по умолчанию — `newest`; `duration` показывает сначала короткие курсы. `status` также позволяет отбирать обучение по прогрессу: `not_started`, `in_progress`, `completed`. В интерфейсе есть кнопки применения и сброса фильтров.

### Удаление в корзину и восстановление

Удалять и восстанавливать мероприятия и курсы могут руководители и администраторы. Перед действием интерфейс показывает подтверждение с названием записи. Удаление сохраняет связанные данные: заявки, подтверждённые часы, материалы и прогресс обучения. Обычные каталоги не включают записи с `archived_at`; сотрудники могут получить корзину через `archived=true` в списках мероприятий и курсов. Варианты фильтров мероприятий также принимают `archived=true`. Волонтёрам общий архив недоступен.

- `POST /api/opportunities/:id/archive` — переместить мероприятие в корзину и закрыть набор. `POST /api/opportunities/:id/restore` — восстановить с закрытым набором. Неопубликованные черновики сохраняют статус `draft` при обоих действиях. Ответ `{ item }`. Методы клиента: `api.opportunities.archive(id)`, `.restore(id)`.
- `POST /api/courses/:id/archive` и `/restore` принимают `{ expected_version }`, ответ `{ item }`. Методы клиента: `api.courses.archive(id, version)`, `.restore(id, version)`. Восстановление возвращает прежний статус публикации; интерфейс сообщает об этом перед подтверждением. Если версия изменилась, сервер возвращает `409`.
- Удалить курс, используемый как подготовка в действующем открытом мероприятии или черновике, нельзя (`409`): сначала замените или уберите ссылку в мероприятии.

Удалённое мероприятие недоступно для редактирования, новых откликов и приглашений. Напоминания и рассылки по нему прекращаются. Чтение истории и учёт часов уже принятых участников сохраняются. Волонтёр может открыть архивную карточку своего отклика при сохранении прав на публичное событие или действующего приглашения.

Архивные курсы убираются из обязательного маршрута, новые записи на них запрещены. `GET /api/courses?history=true` возвращает волонтёру его доступные архивные курсы, на которые он уже записан. Правила аудитории и срока доступа продолжают действовать. Удаление и восстановление записываются в аудит; рабочая выгрузка содержит `archived_at` и `archived_by`.

```js
const events = await api.opportunities.list({
  q: "Керамика",
  status: "open",
  page: 1,
  page_size: 50,
});
// Следующая страница с теми же фильтрами:
const nextEvents = await api.opportunities.list({
  q: "Керамика",
  status: "open",
  page: 2,
  page_size: 50,
});
const { item: event } = await api.opportunities.get(eventId);
const roster = await api.opportunities.participants(event.id, {
  q: "Анна",

const people = await api.users.list({
  q: searchText,

```

В выпадающих списках также нужны поиск и страницы: первая страница событий, участников или пользователей не является полным справочником. Показывайте общее число результатов, сохраняйте явно выбранную запись при переходе на другую страницу и не подменяйте её первым результатом. При записи часов конкретному участнику проверяйте существующую запись запросом `/participation?user_id=…&opportunity_id=…`.

`full_name` — 2–120 символов; `city` — до 120; e-mail нормализуется сервером. `gender` принимает `female`, `male`, `unspecified`, по умолчанию `unspecified`. Дата рождения — `YYYY-MM-DD`, не раньше 1900 года и не в будущем. Пароль регистрации и новый пароль: от 12 до 128 символов, без обрезания пробелов и Unicode. Повтор пароля проверяется только на фронтенде, его не нужно отправлять. Оба согласия должны быть булевым `true`; показывайте ссылки из `/config`.

Показывайте активное начало регистрации только при `registration_enabled && email_verification_available`. Первый флаг означает разрешение регистрации и наличие обязательных ссылок в production; второй — наличие конфигурации выбранного почтового транспорта. Он не гарантирует успешную доставку каждого письма. Без почтового транспорта начало регистрации и повторная отправка отвечают `503` с `code: 'email_verification_unavailable'`; при ошибке отправки — `503` с `code: 'email_delivery_failed'` и `retry_after: 30`. Пользователь при этом не создаётся. Уже доставленный действующий код можно подтвердить даже при последующем отключении транспорта, пока `registration_enabled: true`: не блокируйте форму проверки такого кода. На сервере выбирается `MAIL_TRANSPORT=unisender_go` или `smtp` с соответствующими параметрами из [MAIL.md](MAIL.md); эти настройки и секреты не передаются во фронтенд. `EMAIL_DEMO_ACCOUNTS` не включает регистрацию без письма.

Обычный код состоит ровно из 4 случайных цифр (например, `0042`), никогда не равен `1234`, действует 10 минут и допускает 5 неверных попыток. Повторная отправка разрешена через 30 секунд, до 5 писем в час на один e-mail; дополнительные лимиты действуют по IP. Новый код заменяет предыдущий. Ошибочный, просроченный или исчерпавший попытки код возвращает `400` с `code: 'invalid_verification_code'`. При `429` используйте `ApiError.retryAfter` — число секунд ожидания. Не превращайте код в число: ведущие нули значимы. Длину для нового интерфейса можно прочитать из `code_length` в ответе регистрации/повторной отправки или `email_verification_code_length` в `/config`. Используйте текстовое поле с `inputmode="numeric"`, `autocomplete="one-time-code"` и ограничением на 4 цифры. Ранее выданные шестизначные коды после обновления не принимаются; запросите новый код в той же сессии. Миграция БД для этого изменения не требуется.

Регистрация привязана к cookie-сессии, в которой отправлена форма. Ввод и повторная отправка кода должны происходить в том же браузере и с тем же адресом API. При утрате cookie предложите начать регистрацию заново; сохранённого e-mail недостаточно для восстановления сессии. Не выполняйте logout или login между отправкой формы и подтверждением. `202` не означает вход: не очищайте CSRF и не создавайте фиктивного пользователя. Действующие ранее созданные аккаунты и учётная запись администратора продолжают входить без нового кода. Забытому паролю этот маршрут не служит заменой.

`PATCH /me` сохраняет ФИО, город, телефон, дату рождения и пол. Отправляйте текущие значения контактных полей целиком: пропущенные необязательные контакты очищаются. Пропущенный `gender` сохраняется. После первого сохранения расширенной анкеты её поля `skills`, `interests`, `experience`, `participation_format`, `participation_frequency` управляются только через `/questionnaire`; `/me` сохраняет их текущие значения. Для старых пользователей без анкеты `/me` ещё поддерживает эти поля: пропущенные массивы очищаются. Пример обновления контактов с сохранением старых полей:

```js
const { user } = await api.profile.get();
await api.profile.update({
  full_name: "Анна Иванова",
  city: "Москва",
  phone: "+7 ...",
  birth_date: null,
  gender: user.gender,
  skills: user.skills,
  interests: user.interests,
  experience: user.experience,
  participation_format: user.participation_format,
  participation_frequency: user.participation_frequency,
});
```

Изменение `email`, `role` или `status` через `/me` не поддерживается.

| `GET /users/:id/questionnaire` | Координатор — анкеты волонтёров; руководитель и администратор — также сотрудников | Такой же ответ                                                         |

Готовые методы: `api.questionnaire.get()`, `api.questionnaire.update(fields)`, `api.users.questionnaire(userId)`. Справочники приходят в `options`: массивы подсказок `hobbies`, `skills`, `help_directions`, `professional_education` и списки `{ value, label }` для `occupations`, `volunteering_durations`, `preferred_formats`, `weekdays`, `skill_levels`.

`PATCH /questionnaire` заменяет **всю анкету**. Загружайте её перед редактированием и отправляйте полный объект `questionnaire`, а не весь ответ API. Пропущенные поля становятся пустыми или `null`; неизвестные поля отклоняются. `submit: false` сохраняет черновик, `submit: true` отправляет анкету после проверки почты и согласий. `missing_fields` — подсказки о незаполненных группах; они не блокируют отправку. `completed_at` сохраняет дату первой отправки и не сбрасывается последующим редактированием.

| Поле                                                                                  | Формат                                                                                     |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `hobbies`, `help_directions`, `professional_education`                                | Массив строк: до 30 элементов по 1–80 символов; повторяющиеся значения объединяются        |
| `skills`                                                                              | До 30 уникальных `{ name: string, level: 1 \| 2 \| 3 \| 4 }`; название до 80 символов      |
| `occupation`                                                                          | `school`, `college_university`, `study_and_work`, `work`, `not_study_or_work` или `null`   |
| `occupation_field`, `education_institution`                                           | Строки до 500 и 300 символов                                                               |
| `has_volunteer_experience`, `has_organizing_experience`, `has_professional_education` | `true`, `false` или `null`, если ответа пока нет                                           |
| `experience_direction`, `experience_liked`                                            | Строки до 1000 и 2000 символов                                                             |
| `volunteering_duration`                                                               | `under_3_months`, `3_9_months`, `about_year`, `1_3_years`, `over_3_years` или `null`       |
| `preferred_format`                                                                    | `online`, `in_person`, `mixed`, `depends` или `null`                                       |
| `availability`                                                                        | `{ mon, tue, wed, thu, fri, sat, sun }`: часы от 0 до 24 с шагом 0.5; пропущенный день — 0 |

При `has_volunteer_experience: false` сервер очищает описание прошлого опыта, ответ об организации и длительность. При `has_professional_education: false` очищает список профильного образования. `missing_fields` помогает предложить пользователю дополнить интересы, навыки, направления помощи, занятость, опыт, формат и доступное время. Не превращайте эти подсказки в дополнительные обязательные вопросы.

```js
const { questionnaire: draft, options } = await api.questionnaire.get();
const saved = await api.questionnaire.update({
  ...draft,
  hobbies: ["Музыка и искусство"],
  skills: [{ name: "Работа в команде", level: 3 }],
  help_directions: ["Проведение творческих занятий"],
  preferred_format: "mixed",
  availability: { ...draft.availability, sat: 3 },
});
// saved.missing_fields может быть непустым — черновик всё равно сохранён.
const { user: refreshedUser } = await api.profile.get();
```

Анкета и производные поля профиля сохраняются одной транзакцией. Названия навыков попадают в `user.skills`, направления помощи — в `user.interests`; опыт, формат и расписание формируют текстовые поля профиля. Увлечения и уровни навыков сохраняются в расширенной анкете. После изменения обновите `/me` и список возможностей, чтобы показать актуальные совпадения тегов.

## События, отклики и учёт часов

| Метод и путь                          | Кто            | Запрос / ответ                                                                                           |
| ------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------- |
| `GET /opportunities`                  | Все вошедшие   | Страница; каждый элемент содержит `my_application`, `my_application_id`, `accepted_count`, `match_score` |
| `POST /opportunities`                 | Руководитель+  | Создание события → `201 { item }`                                                                        |
| `PATCH /opportunities/:id`            | Руководитель+  | Частичное изменение полей → `{ item }`                                                                   |
| `GET /opportunities/:id/participants` | Координатор+   | Страница со статусами и `required_completed`, `required_total`, `hours`                                  |
| `POST /opportunities/:id/apply`       | Волонтёр       | `{ note? }` → `201 { application }`                                                                      |
| `GET /applications`                   | Все вошедшие   | Страница своих / доступных сотруднику откликов; фильтры приведены выше                                   |
| `PATCH /applications/:id`             | По правам ниже | `{ status }` → `{ application }`                                                                         |
| `GET /participation`                  | Все вошедшие   | Страница своих / доступных сотруднику участий; `summary: { entries, total_hours }` для всей выборки      |
| `POST /participation`                 | Координатор+   | Запись участия → `201 { item }`                                                                          |
| `PATCH /participation/:id`            | Координатор+   | `{ hours, participated_on?, note? }` → `{ item }`                                                        |

Сценарий создания события сотрудником:

```js
const { item: event } = await api.opportunities.create({
  title: "Творческая суббота",
  description: "Помощь на занятии по керамике.",
  city: "Москва",
  format: "Очно",
  location: "Мастерские фонда",
  starts_at: "2026-11-14T08:00:00.000Z",
  ends_at: "2026-11-14T11:00:00.000Z",
  status: "draft",
  capacity: 12,
  skills: ["Керамика"],
  interests: ["Творчество"],
});
await api.opportunities.update(event.id, { status: "open" });
```

`title` — 3–200 символов, `description` — 3–8000. Статусы: `draft`, `open`, `closed`; если статус при создании не задан, сервер использует `open`, поэтому для подготовки события явно отправляйте `draft`. `capacity` — положительное целое до 100000 или `null` без ограничения. Конец должен быть позже начала. Уменьшить лимит ниже числа принятых участников нельзя.

Карточку события загружайте через `GET /opportunities/:id` → `{ item }`; не ищите её перебором страниц `/opportunities`. Волонтёр не видит чужие отклики и черновики. Откликаться могут только пользователи роли `volunteer` на открытые события; повторный отклик возможен после отзыва предыдущего.

```js
// В кабинете волонтёра:
const { application } = await api.opportunities.apply(
  eventId,
  "Готова помочь с материалами.",
);

// В отдельной сессии координатора:
await api.applications.updateStatus(applicationId, "accepted");
const roster = await api.opportunities.participants(eventId, {
  status: "accepted",
  page: 1,
});
// Пользователь выбирает участника из списка с поиском и страницами.
const participant = roster.items.find(
  (person) => String(person.user_id) === String(selectedUserId),
);
if (!participant)
  throw new Error("Выберите участника из загруженной страницы.");

// После фактического участия:
await api.participation.create({
  user_id: participant.user_id,
  opportunity_id: eventId,
  participated_on: "2026-11-14",
  hours: 3,
  note: "Подготовка материалов и помощь на занятии.",
});
```

Используйте ID из ответов API, а в интерфейсе показывайте имя волонтёра и название события. Допустимые статусы отклика: `pending`, `accepted`, `rejected`, `withdrawn`. Волонтёр может только отозвать свой отклик; сотрудники управляют статусами. При подтверждении сервер проверяет вместимость. Если участие уже записано, снять подтверждение отклика нельзя.

Для связанных с событием часов нужен подтверждённый отклик. На пару «волонтёр + событие» допускается одна запись: при исправлении используйте `PATCH /participation/:id`. Часы должны быть больше 0 и не больше 24 на запись. Исправление меняет только `hours`, дату и комментарий, не пользователя, событие или название. Для отдельной задачи без события передавайте `opportunity_id: null` и обязательное `title` длиной 2–200 символов.

## База волонтёров и управление доступом

| Метод и путь                   | Кто                                                        | Запрос / ответ                                                                                   |
| ------------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `GET /users`                   | Координатор+                                               | Страница; фильтры `q`, `city`, `skill`, `status`, `role`, `page`, `page_size`                    |
| `POST /users`                  | Руководитель+                                              | `{ full_name, email, comment? }` → `201 { user }`; новая карточка волонтёра со статусом `new`    |
| `GET /users/:id`               | Координатор+                                               | `{ user, participation, applications, training, notes?, summary }`; истории — отдельные страницы |
| `GET /users/:id/questionnaire` | Координатор+ с ограничениями роли целевого пользователя    | `{ questionnaire, options, updated_at, completed_at, missing_fields }`                           |
| `PATCH /users/:id/status`      | Координатор+ для волонтёров; администратор для сотрудников | `{ status }` → `{ user }`                                                                        |
| `PATCH /users/:id/role`        | Администратор                                              | `{ role }` → `{ user }`                                                                          |
| `POST /users/:id/notes`        | Руководитель+                                              | `{ body }`, 1–4000 символов → `201 { item }`                                                     |
| `POST /users/:id/thanks`       | Координатор+                                               | `{ message }`, 2–2000 символов → `201 { item }`                                                  |

`q` ищет имя или e-mail, `city` и `skill` допускают поиск по части строки. Статусы пользователя: `new`, `active`, `paused`, `closed`. Страница начинается с 1. Координатор получает в списке только волонтёров; руководитель и администратор — также сотрудников. Карточка содержит рабочие контакты, историю участия, откликов и прохождения материалов; `notes` и расширенные персональные поля возвращаются руководителям и администраторам.

```js
const page = await api.users.list({
  q: "Анна",
  city: "Москва",
  status: "active",
  page: 1,
});
const card = await api.users.get(page.items[0].id);
await api.users.updateStatus(card.user.id, "active");
// Из административной сессии:
await api.users.updateRole(userId, "coordinator");
```

**Изменение контракта карточки:** `participation`, `applications`, `training` и доступное руководителю `notes` теперь содержат конверты страниц, а не массивы. Читайте, например, `card.participation.items`. Параметры `participation_page`, `applications_page`, `training_page`, `notes_page` управляют историями независимо; общий `page_size` ограничивает каждую из них. `summary` содержит `total_hours`, `participation_count`, `application_count`, `training_count`, `training_completed`, `required_training_total`, `required_training_completed` по всей карточке.

```js
const card = await api.users.get(userId, {
  participation_page: 2,
  applications_page: 1,
  training_page: 1,
  notes_page: 1,
  page_size: 50,
});
const participationRows = card.participation.items;
const allHours = Number(card.summary.total_hours);
```

После изменения собственной рабочей сессии другим администратором обновляйте `/me` и перестраивайте интерфейс. Даже если фронтенд ещё показывает старую кнопку, сервер уже применяет актуальные права.

| --------------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |

| `GET /training/:id`               | Все вошедшие         | `{ item }` с `completed` и `completed_at` текущего пользователя; неопубликованный материал доступен только сотрудникам                        |

`training.title` — 2–200 символов, описание — до 4000. Ссылка — `http://` или `https://`, пустая строка или `null`; `required` и `published` — булевы значения. Если не указаны, сервер использует `required: false`, `published: true`. Ознакомление — самостоятельная отметка пользователя, не результат экзамена. Скрытые материалы волонтёру недоступны.

Уведомления создаются сервером при публикации/изменении событий, откликах, изменении их статусов, записи/исправлении часов и благодарностях. Это сообщения внутри кабинета. Почта используется для кода регистрации; рассылки событий по e-mail, Telegram, SMS и push не реализованы. Для актуализации счётчика используйте `api.notifications.unreadCount()` при открытии раздела или возвращении пользователя во вкладку; WebSocket/SSE API отсутствует.

```js
{
  users: [{ role: 'volunteer', status: 'active', count: 18 }],
  hours: { total_hours: '42.50', entries: 12 },
  registrations: [{ month: '2026-10-01', count: 5 }],
  cities: [{ city: 'Москва', count: 18 }],
  opportunities: [{ status: 'open', count: 3 }]
}
```

Это пример формы ответа, не статистика фонда. Журнал содержит `actor_name`, `action`, `subject_type`, `subject_id`, `created_at`. Все перечисленные выше списки загружаются постранично; не используйте первую страницу как полную историю.

## Выгрузка данных администратором

Большие файлы скачиваются средствами браузера: frontend получает одноразовую ссылку и открывает её нативным download-переходом. Файл не собирается в `Blob`, `ArrayBuffer` или строку в памяти страницы.

1. `POST /api/admin/exports/prepare` с JSON `{ format: 'backup' | 'json' | 'csv', current_password: '…' }` → `{ download_url, expires_at }`.
2. Сразу откройте `download_url` обычной ссылкой. Это `GET /api/admin/exports/download/<token>` с cookie текущей сессии. Не вызывайте `fetch`, prefetch, HEAD или проверку ссылки перед скачиванием.

Подготовка требует текущего администратора, CSRF и повторного ввода пароля. Пароль отправляется только в JSON-теле HTTPS-запроса и не хранится после операции. Ссылка действует 60 секунд, одноразовая, привязана к пользователю, сессии и версии авторизации. После выхода, смены пароля или неудачной использованной загрузки подготовьте новую ссылку. Не записывайте её в логи или постоянное хранилище и не отправляйте другим людям.

| `format` | Файл и содержимое                                                                                                                                                                                                     |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `backup` | `.dump` — архив PostgreSQL для восстановления, включая хеши паролей. Активные сессии и неподтверждённые регистрации исключены. Содержит персональные данные и требует защищённого хранения; в PGlite demo недоступен. |
| `json`   | Связанные рабочие таблицы, включая профили, анкеты, приглашения, задачи, заметки и журнал. Авторизационные секреты и служебные таблицы сессий/регистрации не включаются.                                              |
| `csv`    | UTF-8 с BOM: волонтёры, часы, сводные показатели и анкеты. Значения защищены от исполнения формул при открытии таблицей.                                                                                              |

```js
const ticket = await api.admin.prepareExport("csv", enteredPassword);
const link = document.createElement("a");
link.href = ticket.download_url;
link.download = ""; // Имя файла задаёт сервер через Content-Disposition.
link.rel = "noreferrer";
document.body.append(link);
link.click();
link.remove();
// Покажите «Запрос на скачивание передан браузеру», а не «Файл скачан».
```

Метод клиента проверяет ссылку и разрешает её относительно origin API. Для отдельного frontend предпочтителен тот же origin через `/api` proxy: скачивание должно попасть на backend с cookie той же сессии. Не переписывайте URL на другой домен и не добавляйте к нему пароль/CSRF. Ошибки подготовки — обычные `ApiError`; ход и ошибки потоковой загрузки после перехода отображает браузер.

**Изменение клиента:** `api.admin.exportData(...)` оставлен как алиас `prepareExport(...)`, но теперь возвращает `{ download_url, expires_at }`, не `{ blob, filename }`. Обновите старые вызовы с `URL.createObjectURL`. Опция `{ signal }` отменяет только подготовку ссылки, не нативную загрузку после клика.

Действует лимит пяти подготовок в час на администратора и одной выполняющейся выгрузки одновременно. Фиксированного ограничения по числу строк или размеру файла нет; сервер передаёт данные потоком, без временного файла, с ограничением времени 15 минут. Проверяйте завершение в загрузках браузера. Для восстановления по-прежнему нужны серверные инструменты PostgreSQL; маршрута загрузки `.dump` в API нет.

Старый `POST /api/admin/export` с тем же JSON-телом и CSRF сохраняет совместимый ответ-вложение и также передаёт его потоком. Он предназначен для клиентов, умеющих писать поток сразу на диск. Для браузерного интерфейса используйте `prepareExport`, чтобы не накапливать файл в памяти страницы.

## Ошибки и состояние интерфейса

Обычная ошибка: `{ "error": "Понятное сообщение" }`. Валидация возвращает `details: [{ path: ['название_поля'], message: '…' }]`; CSRF добавляет `code: 'CSRF_INVALID'`.

| Статус                | Действие фронтенда                                                                                                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `400`                 | Показать ошибки полей, сохранить введённые данные                                                                                                                                 |
| `401`                 | На форме входа показать отказ; в кабинете запросить повторный вход                                                                                                                |
| `403`                 | Недостаточно прав / origin не разрешён; CSRF-клиент сам обрабатывает только `CSRF_INVALID`                                                                                        |
| `404`                 | Запись не найдена или недоступна; вернуться к списку                                                                                                                              |
| `409`                 | Конфликт состояния: места закончились, запись уже существует, часы уже записаны; обновить данные                                                                                  |
| `413`                 | Уменьшить тело JSON-запроса                                                                                                                                                       |
| `429`                 | Показать сообщение об ограничении попыток; `error.retryAfter` — секунды из JSON `retry_after` либо заголовка `Retry-After`, или `null`                                            |
| `503`                 | Показать причину временной недоступности: например, `DATABASE_BUSY` с `Retry-After: 3`, ошибка доставки письма или создания архива. Не повторять изменяющие запросы автоматически |
| `500`                 | Сообщить об ошибке сервера и дать повторить загрузку                                                                                                                              |
| `status: 0` у клиента | Ошибка сети/блокировка браузером; не выдавать её за неверный пароль                                                                                                               |

```js
try {

} catch (error) {
  if (!(error instanceof ApiError)) throw error;
  if (error.status === 409) {
    // Покажите error.message и обновите список участников.
  } else if (error.status === 401) {
```

## Закрытые мероприятия и приглашения

К полям мероприятия добавлено `visibility: 'public' | 'invite_only'`; по умолчанию `public`, старые события остаются публичными. Сотрудники видят все события. Волонтёр видит закрытое событие только при активном приглашении и допустимом статусе события; черновики скрыты. Приглашение само по себе не является принятой заявкой и не резервирует место.

| Маршрут                                        | Доступ                            | Результат                                                                                                    |
| ---------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `GET /opportunities/:id`                       | Сотрудник или волонтёр с доступом | `{ item }` с `my_application`, `my_invitation`, `accepted_count`, `match_score`; недоступное событие — `404` |
| `GET /opportunities/:id/invitations`           | Координатор+                      | Страница приглашений; фильтры `q`, `status`, `page`, `page_size`                                             |
| `POST /opportunities/:id/invitations`          | Координатор+                      | `{ user_ids: [id, ...] }` (1–100) → `201 { items, invited_count }`                                           |
| `PATCH /opportunities/:id/invitations/:userId` | Координатор+                      | `{ status: 'revoked' }` → `{ item }`                                                                         |

Приглашать можно пользователей с ролью `volunteer` и статусом `new` или `active`. Повторная отправка активного приглашения не создаёт второе уведомление; отозванное приглашение можно активировать заново. Приглашения доступны и для публичных мероприятий, чтобы подготовить их перевод в закрытые. Если у действующей заявки (`pending` или `accepted`) нет активного приглашения, перевод `public → invite_only` вернёт `409`.

При отзыве приглашения ожидающий отклик переводится в `withdrawn` в той же транзакции. Принятый отклик сначала нужно отклонить/отозвать; если участие уже учтено, отзыв приглашения запрещён (`409`). После отзыва волонтёр сохраняет историю своего отклика, но она не даёт доступа к новым сведениям о закрытом событии. Ограничения проверяются и при прямом запросе API, и при принятии/восстановлении заявки сотрудником.

Методы клиента: `api.opportunities.get(id)`, `.invitations(id, filters)`, `.invite(id, userIds)`, `.revokeInvitation(id, userId)`.

## Задачи команды по сопровождению волонтёра

Это внутренние задачи сотрудников: например, провести вводную встречу или уточнить доступность волонтёра. Волонтёры не имеют доступа к этому API (`403`). Координатор читает и меняет задачи о волонтёрах, созданные им или назначенные ему; создавать/переназначать он может только на себя. Руководитель и администратор видят все задачи и назначают любого сотрудника со статусом `active`.

| Маршрут                  | Тело / фильтры                                                                        | Результат                                             |
| ------------------------ | ------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `GET /staff-tasks`       | `mine=true`, `user_id`, `status`, `overdue=true`, `page`                              | `{ items, page, page_size: 50, total, pages }`        |
| `GET /staff-tasks/:id`   | —                                                                                     | `{ item }`; чужая задача для координатора — `404`     |
| `POST /staff-tasks`      | `user_id`, `assigned_to`, `title`, необязательные `description`, `due_at`, `priority` | `201 { item }`, начальный статус `open`, `version: 1` |
| `PATCH /staff-tasks/:id` | `expected_version` и изменяемые поля, включая `status`                                | `{ item }` с увеличенной `version`                    |

`title` — 3–200 символов, `description` — до 4000; `due_at` — ISO 8601 с `Z`/смещением либо `null`. Приоритет: `low`, `normal` (по умолчанию), `high`. Статусы: `open`, `in_progress`, `done`, `cancelled`. Поле `user_id` всегда относится к текущему волонтёру. Завершение записывает `completed_at`, повторное открытие очищает его. Удаления задач нет.

В ответе также есть `created_by`, `created_at`, `updated_at`, `user_name`, `assigned_to_name`, `created_by_name`, `is_overdue`. Назначение и изменение фиксируются в журнале. Уведомления о назначении содержат номер задачи без её описания и персональных сведений волонтёра.

Защита от перезаписи чужих изменений:

```js
const { item } = await api.staffTasks.get(taskId);
try {
  await api.staffTasks.update(taskId, {
    status: "done",
    expected_version: item.version,
  });
} catch (error) {
  if (error.code === "TASK_VERSION_CONFLICT") {
    // Загрузите свежую задачу и предложите пользователю повторить изменение.
    // Не повторяйте PATCH автоматически с новой версией.
  } else throw error;
}
```

Методы клиента: `api.staffTasks.list(filters)`, `.get(id)`, `.create(fields)`, `.update(id, fields)`.

## Достижения и автоматические напоминания

`GET /achievements` возвращает собственный прогресс; `GET /users/:id/achievements` доступен сотрудникам (координатор — только для волонтёров). Формат:

```js
{
  user_id: '42', total_hours: 12.5, activities: 3,
  items: [{
    key: '10h', title: '10 часов помощи',
    description: '10 подтверждённых часов волонтёрской работы',
    threshold: 10, progress: 10, earned: true, unit: 'hours'
  }]
}
```

Ключи: `first_activity` (единица `activities`), `10h`, `50h`, `100h` (единица `hours`). У сотрудника массив пустой. В прогресс входят только положительные часы с датой участия не позже текущего дня базы. Это производный показатель: исправление записи участия немедленно влияет на ответ API; ошибочно выданное ранее уведомление остаётся в истории. Уведомление о каждом достижении создаётся один раз за всё время. Методы клиента: `api.achievements.get()`, `api.users.achievements(id)`.

Планировщик работает внутри приложения сразу после запуска и затем раз в 60 секунд:

- Участники с принятым откликом получают напоминание при попадании события в окно до 24 часов и затем до 2 часов. При первом запуске внутри двухчасового окна приходит только ближайшее напоминание. Событие должно быть открыто и ещё не начаться, волонтёр — `new`/`active`; для закрытого события нужно активное приглашение. Перенос начала создаёт новый ключ напоминания.
- Исполнитель получает одно напоминание о просроченной задаче для каждой пары «срок + исполнитель», пока задача `open`/`in_progress`. Закрытые аккаунты и пользователи без права доступа не уведомляются.
- После записи часов вычисляются достижения. Просроченные сессии очищаются небольшими порциями.

Все эти сообщения приходят **в кабинет**. SMTP, отдельный процесс, Redis и очередь не нужны. Реестр в PostgreSQL предотвращает повторную отправку при перезапуске, а блокировка в БД исключает одновременный проход двух экземпляров приложения. После простоя уже начавшиеся события не получают запоздалое напоминание. Большая очередь обрабатывается порциями за несколько проходов.

`GET /admin/automation` (администратор; `api.admin.automation()`) показывает `interval_ms`, `last_attempt_at`, `last_success_at`, `last_failure_at`, `last_failure_code`, `success_count`, `failure_count`, `last_counts`. Коды сбоя: `database_unavailable`, `database_busy`, `automation_failed`. Старое поле ошибки сохраняется после восстановления; актуальность определяйте сравнением `last_success_at` и `last_failure_at`. В ответе нет текстов SQL и персональных данных; ручного запуска через API нет.

## Фильтрация аналитики и уведомлений

`GET /analytics?date_from=2026-10-01&date_to=2026-10-31` (руководитель+) принимает календарные даты `YYYY-MM-DD`; границы включены, время для группировок — UTC. Метод клиента: `api.analytics.get({ date_from, date_to })`.

- `hours` и новый `monthly_activity` используют `participated_on`. Часы включают все записанные участия в выбранном периоде, а достижения дополнительно исключают будущие даты.
- `registrations` использует дату создания аккаунта. Без обеих границ сохраняется прежний период последних 12 месяцев.
- `opportunities` использует дату начала. События без даты учитываются только при отсутствии фильтров.
- `users` и `cities` остаются текущим снимком базы, без фильтра периода.
- `onboarding` — текущая сводка по незакрытым волонтёрам: `volunteers`, `email_verified`, `questionnaire_completed`, `required_training_completed`, `required_materials`. Обучение учитывает прежние обязательные материалы и уроки опубликованных обязательных курсов, доступных по статусу пользователя и срокам курса. Урок засчитывается только для текущего `content_hash`. Дополнительные поля: `legacy_required_materials`, `required_courses`, `required_course_lessons`. При отсутствии обязательных материалов условие завершения выполнено; интерфейс показывает «Обязательных материалов нет».

`monthly_activity`: `[{ month, total_hours, entries, volunteers }]`; `hours` теперь содержит также число уникальных `volunteers`. Поле `period` сообщает применённые границы и `timezone: 'UTC'`. Все части одного ответа читаются из согласованного снимка БД.

Уведомления поддерживают `api.notifications.list({ page, page_size, unread: true })`. `total`/`pages` учитывают фильтр, `unread` всегда считает все собственные непрочитанные сообщения, независимо от страницы. `api.notifications.unreadCount()` получает только глобальный счётчик без текстов сообщений. `api.notifications.markAllRead()` помечает все собственные сообщения; новые сообщения, пришедшие после операции, останутся непрочитанными.

Новые формы управления приглашениями, задачами и отображения достижений нужно подключить в разрабатываемом фронтенде: серверные методы и клиент уже готовы. В существующем прототипе обновлены список уведомлений, фильтр непрочитанных и массовая отметка прочтения; напоминания и достижения видны как уведомления.

- Демонстрационные записи отмечаются в названиях «· демо» и в именах «Демо ·». Они являются записями PostgreSQL и открываются через обычные API, а не захардкожены в интерфейсе. Добавление выполняется отдельным seed-скриптом; UI сохраняет явные метки из данных.
